GIT - INTERVIEW PREP NOTES
(Last updated: 2026-08-15)

CORE MODEL
- Git tracks snapshots of the whole repo (not diffs) — each commit points to a full tree of file contents, deduplicated via content-addressed storage.
- Three areas: working directory (your files), staging area/index (git add), and the repo/history (git commit).
- HEAD is a pointer to the current branch's latest commit (or to a specific commit, if in "detached HEAD" state).

BRANCHING & MERGING
- A branch is just a movable pointer to a commit — cheap to create, which is why feature-branch workflows are practical.
- Merge: combines two branches' histories, creating a merge commit (if not fast-forwardable) that has two parents — preserves full history of both branches.
- Rebase: replays one branch's commits on top of another, producing a linear history — rewrites commit hashes, so never rebase commits that have already been pushed/shared unless the team explicitly works that way.
- Fast-forward merge: when the target branch has no new commits since the source branched off, Git just moves the pointer forward — no merge commit created.

RESOLVING CONFLICTS
- Conflicts happen when the same lines were changed differently on both sides being merged/rebased.
- Git marks conflicted regions with <<<<<<<, =======, >>>>>>> markers in the affected files — resolve by editing to the correct final content, then `git add` the resolved file, then continue (`git commit` for a merge, `git rebase --continue` for a rebase).
- Always re-run tests after resolving conflicts — a syntactically resolved conflict can still be logically wrong.

COMMIT HYGIENE
- Write commit messages that explain WHY, not just what changed (the diff already shows what) — helps future readers (including yourself) understand intent.
- Small, focused commits are easier to review, bisect, and revert than one giant commit.
- `git commit --amend` rewrites the most recent commit — never amend a commit that's already been pushed and might be in use elsewhere.

UNDOING THINGS
- `git restore <file>` / `git checkout -- <file>`: discard uncommitted changes to a file.
- `git reset --soft HEAD~1`: undo the last commit, keep changes staged.
- `git reset --mixed HEAD~1` (default): undo the last commit, keep changes but unstaged.
- `git reset --hard HEAD~1`: undo the last commit AND discard the changes entirely — destructive, use with care.
- `git revert <commit>`: creates a NEW commit that undoes a previous commit's changes — safe for already-pushed/shared history since it doesn't rewrite anything.

TAGS & RELEASES
- Tags mark a specific commit as significant (e.g. v1.0.0) — annotated tags (git tag -a) store metadata (message, tagger, date); lightweight tags are just a named pointer.
- GitHub Releases are usually built on top of tags, adding release notes and downloadable artifacts.

REMOTE WORKFLOWS
- `git fetch` downloads new history without merging it into your working branch; `git pull` = fetch + merge (or rebase, if configured) in one step.
- Pull requests are a GitHub/GitLab convention (not core Git) for reviewing and discussing changes before merging into a shared branch.
- Force-pushing (`git push --force`) rewrites remote history — dangerous on shared branches (can overwrite others' work); `--force-with-lease` is the safer variant (fails if the remote has commits you haven't seen).

COMMON INTERVIEW QUESTIONS TO BE READY FOR
- Explain the difference between merge and rebase, and when you'd choose each.
- What's the difference between `git reset` and `git revert`, and why is revert safer for shared history?
- Walk through resolving a merge conflict from start to finish.
- What does `git fetch` do that `git pull` doesn't?
- Why is force-pushing to a shared branch risky, and what's a safer alternative?
