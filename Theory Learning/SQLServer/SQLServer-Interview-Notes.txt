SQL SERVER - INTERVIEW PREP NOTES
(Last updated: 2026-08-15)

RELATIONAL DESIGN & NORMALIZATION
- Normalization (1NF, 2NF, 3NF) removes redundancy: 1NF = atomic columns/no repeating groups, 2NF = no partial dependency on part of a composite key, 3NF = no transitive dependencies on non-key columns.
- Denormalization is a deliberate trade-off for read performance (e.g. a cached "TotalBattles" count) — only after normalization is understood, not as a default.
- Junction/bridge tables (e.g. SuperheroPowers, SuperheroTeams) resolve many-to-many relationships using two foreign keys (often forming a composite primary key).

KEYS & CONSTRAINTS
- Primary key: uniquely identifies a row, usually clustered by default in SQL Server (physically orders the table's data by this key).
- Foreign key: enforces referential integrity — a row in the child table must reference an existing row in the parent (or NULL, if nullable).
- Unique constraint vs primary key: a table can have only one primary key but multiple unique constraints (e.g. Username and Email both unique).
- CHECK constraints enforce domain rules at the database level (e.g. PowerLevel BETWEEN 0 AND 100) — a last line of defense even if application validation is bypassed.

INDEXES
- Clustered index: determines the physical storage order of the table — a table can have only one (typically on the primary key).
- Non-clustered index: a separate structure pointing back to the table's rows — a table can have many; speeds up lookups/filters/sorts on columns that aren't the clustered key.
- Composite indexes: order of columns matters — an index on (Universe, Alignment) helps queries filtering by Universe alone or by Universe+Alignment, but not by Alignment alone.
- Over-indexing slows down writes (every INSERT/UPDATE/DELETE must maintain every index) — index for actual query patterns, not speculatively.

JOINS
- INNER JOIN: only matching rows in both tables.
- LEFT (OUTER) JOIN: all rows from the left table, matched rows from the right (NULLs where no match) — common for "superhero with their teams, including heroes with no team".
- RIGHT JOIN: mirror of LEFT JOIN (rare in practice — usually rewritten as a LEFT JOIN by swapping table order).
- FULL OUTER JOIN: all rows from both sides, matched where possible.
- CROSS JOIN: cartesian product — rarely intentional, usually a sign of a missing join condition (a common accidental-bug source).

TRANSACTIONS & ACID
- Atomicity, Consistency, Isolation, Durability — the guarantees a transaction provides.
- BEGIN TRAN / COMMIT / ROLLBACK — wrap multi-statement operations that must succeed or fail together (e.g. recording a Battle result and updating derived stats).
- Isolation levels (READ UNCOMMITTED, READ COMMITTED [default], REPEATABLE READ, SERIALIZABLE, SNAPSHOT) trade off consistency guarantees against concurrency/performance — higher isolation means more locking/blocking.

STORED PROCEDURES & VIEWS
- Stored procedures encapsulate reusable, parameterized SQL logic server-side — this project's convention prefixes them `xsp` (e.g. xspGetSuperheroRankings).
- Views are saved SELECT queries that behave like virtual tables — useful for simplifying a complex recurring join or for a stable read-only reporting shape.
- Triggers fire automatically on INSERT/UPDATE/DELETE — powerful but can make data flow hard to reason about; use sparingly and only when application-level logic genuinely can't cover the case (e.g. audit trails).

QUERY OPTIMIZATION
- Execution plans (Actual vs Estimated) show how SQL Server will run/ran a query — look for table scans on large tables (often a missing/unused index) vs index seeks (efficient).
- SARGable predicates (Search ARGument ABLE) let the optimizer use an index — e.g. `WHERE Name LIKE 'Bat%'` can use an index, `WHERE UPPER(Name) = 'BATMAN'` generally can't (function wraps the column).
- Avoid SELECT * in application code — fetch only needed columns, especially on wide tables.

WINDOW FUNCTIONS
- ROW_NUMBER(), RANK(), DENSE_RANK() OVER (ORDER BY PowerLevel DESC) — ideal for building rankings (e.g. "Top 10 heroes by power level") without a self-join or subquery.
- PARTITION BY divides rows into groups before the window function is applied — e.g. rank heroes separately within each Universe.

COMMON INTERVIEW QUESTIONS TO BE READY FOR
- Explain normalization briefly, and give an example of when you'd deliberately denormalize.
- Difference between a clustered and non-clustered index.
- What makes a WHERE clause "SARGable", and why does it matter?
- How would you write a query to rank superheroes by PowerLevel within each Universe?
- Explain transaction isolation levels and the trade-off they represent.
