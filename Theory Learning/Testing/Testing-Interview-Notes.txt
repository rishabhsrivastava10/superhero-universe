TESTING - INTERVIEW PREP NOTES
(Last updated: 2026-08-15)

TEST TYPES & THE TESTING PYRAMID
- Unit tests: test a single unit (a method/class) in isolation, dependencies mocked/stubbed — fast, numerous, form the base of the pyramid.
- Integration tests: test multiple components together (e.g. a controller + real DbContext against an in-memory/test database) — fewer, slower, catch wiring/config issues unit tests can't.
- End-to-end (E2E) tests: drive the whole system through the UI like a real user — fewest, slowest, most brittle, but highest confidence that the whole system works together.
- The pyramid shape (many unit, some integration, few E2E) reflects a cost/speed/confidence trade-off, not a hard rule — but a lot of E2E-heavy, unit-light suites are usually a red flag.

AAA PATTERN
- Arrange: set up inputs, mocks, and the object under test.
- Act: call the method/behavior being tested.
- Assert: verify the outcome (return value, thrown exception, or a mock's interaction).
- Keeps tests readable and consistent regardless of framework.

MOCKING & TEST DOUBLES
- Mock: a fake object that records/verifies interactions (e.g. "was SaveChangesAsync called exactly once?").
- Stub: a fake object that returns canned data but isn't verified for interactions.
- Fake: a real, simplified working implementation (e.g. EF Core's InMemory provider acting as a fake database).
- Moq (or NSubstitute) is the common .NET mocking library; mock interfaces (IRepository, IService), not concrete classes — another reason to depend on abstractions.

BACKEND TESTING (.NET)
- xUnit is the most common test framework for modern .NET projects ([Fact] for a single test, [Theory] + [InlineData] for parameterized tests).
- Test business logic directly and thoroughly: battle calculation given specific hero stats, mission success-probability calculation given specific team compositions — these are exactly the kind of pure, deterministic logic that's cheap to test exhaustively.
- Controller/integration tests can use WebApplicationFactory<Program> to spin up the app in-memory and hit real HTTP endpoints against a test database.
- Test authentication logic: password hashing round-trips correctly, invalid credentials are rejected, expired/tampered tokens are rejected.

FRONTEND TESTING (ANGULAR)
- Service tests: mock HttpClient (via HttpTestingController) and verify the service builds the right request and handles the response/error correctly.
- Component tests: use TestBed + ComponentFixture; test what the user would observe (rendered output, emitted events) rather than internal implementation details.
- Form validation tests: assert a FormControl reports the right errors for invalid input, and no errors for valid input.
- Auth guard tests: verify the guard blocks/allows navigation correctly for authenticated/unauthenticated/wrong-role scenarios.

WHAT TO PRIORITIZE (ESPECIALLY FOR THIS PROJECT)
- Battle simulation algorithm: deterministic inputs should produce the exact expected winner/scores — a prime target for [Theory]-driven parameterized tests covering edge cases (a hero battling itself should be rejected, tie-breaking rules, etc.).
- Mission success-probability calculation: same idea — cover boundary conditions (0 heroes, exactly the required count, more than required, mismatched difficulty).
- Auth flows: registration validation, duplicate username/email handling (409), login failure paths.
- Avoid writing trivial tests just to inflate a coverage number (e.g. testing that a DTO's properties can be set) — focus effort where real logic/bugs live.

MAKING RANDOMNESS TESTABLE (APPLIED IN THIS PROJECT'S BATTLE SIMULATOR)
- Calling Random.Shared directly inside business logic makes that logic untestable: you can never assert an exact outcome, so the best you can do is loose range checks.
- Fix: put the randomness behind a tiny interface (here IBattleVarianceProvider with a single NextVariance() method) and inject it. Production registers the real implementation; tests inject a fixed-value stub and get fully deterministic results, so you can assert exact scores.
- The same trick applies to DateTime.Now (inject an IClock/TimeProvider), Guid.NewGuid(), and anything else non-deterministic. .NET 8+ ships TimeProvider specifically for the clock case.
- Random.Shared is thread-safe; a single shared `new Random()` instance is NOT, and concurrent calls can return duplicate/zero values. Use Random.Shared, or one Random per thread.

TESTING PROBABILISTIC BEHAVIOUR WITHOUT A STUB
- You can still assert useful things end-to-end without controlling the seed:
  * Invariants that must ALWAYS hold - e.g. the winner is whoever has the higher score; the loser is the other combatant; scores stay within 0-100.
  * Outcomes that variance must never flip - a hero with an overwhelming attribute advantage should win 12/12 runs. If that ever fails, the variance range is too wide.
  * Outcomes that variance SHOULD flip - two near-identical heroes should not produce the same winner 20/20 times, and repeated identical matchups should not produce identical scores. This is what proves the randomness is actually wired in rather than silently stubbed out.
- Storing a computed result matters too: fetching a historical record must return the SAVED scores, not re-run the calculation. Re-simulating would silently rewrite history. Worth an explicit test.

COMMON INTERVIEW QUESTIONS TO BE READY FOR
- Explain the testing pyramid and why E2E-heavy suites are usually a problem.
- What's the difference between a mock and a stub?
- How would you unit test a method that depends on DateTime.Now or randomness (like a battle simulator)? (Answer: inject a clock/random abstraction so it's deterministic and controllable in tests.)
- How do you test an ASP.NET Core controller without hitting a real database?
- Why prioritize testing business logic over auto-generated boilerplate?
